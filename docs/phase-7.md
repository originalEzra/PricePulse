# Phase 7：性能对比与故障实验

## 实验范围

本阶段验证规则索引的查询成本、集中通知的积压与消化，以及异常后的业务对账。Testcontainers 创建全新的 MySQL 和 Redis，完成后自动清理；RocketMQ 使用现有 Compose Broker，但每次生成独立的 Topic、Producer Group 和 Consumer Group。

不会重启或停止现有 Compose MySQL、Redis、Broker，也不会把测试规则写进日常开发数据库。MQ 中会留下以 price-pulse-perf- 开头的测试主题与消费组，可在清理测试 Broker 时一并移除。

不需要安装额外压测工具。测试使用 JDK HTTP Client、现有 Spring Boot 服务、MySQL、Redis 和真实 RocketMQ。数据准备走 JDBC 批量写入，排除在业务吞吐计时之外。

## 一键复现

需要已运行的 Docker Desktop 和 JDK 21+：

~~~bash
bash scripts/run-performance.sh
~~~

脚本确保本地 MQ 已启动，然后执行：

~~~bash
./mvnw -B -ntp -Pperformance verify
~~~

快速检查：

~~~bash
bash scripts/run-performance.sh -Dperf.scales=1000 -Dperf.samples=50 -Dperf.burst=50
~~~

| 参数 | 默认值 | 范围或含义 |
| --- | --- | --- |
| perf.seed | 20261027 | 固定规则和价格区间分布 |
| perf.scales | 1000,10000,50000 | 最多 5 档，每档 100–200000 条规则 |
| perf.samples | 150 | 每档有效对比样本数，50–1000 |
| perf.burst | 500 | 单次集中触发数量，10–5000 |
| ROCKETMQ_NAMESERVER | 127.0.0.1:19876 | 测试 Broker 的 NameServer |

生成 target/performance/run-UUID.json、同名 Markdown 和 latest.*。失败会将状态写为 FAILED，不能当作整轮通过。JSON 保留每次计时、配置、时间、组件版本、JVM 堆上限、Docker 内存和源码 SHA-256。

源码指纹覆盖 src/main、本阶段性能测试代码和 pom.xml。报告里的 Git SHA 是实验开始时的基准提交；实验代码尚未提交时 worktreeDirtyAtRun=true，应以源码指纹核对最终版本。

## 1. 候选匹配对比

为同一只股票分别准备 1000、10000、50000 条规则，均匀包含生效的上破、下破规则，以及冷却中的双向规则和重新激活价。阈值约分布在 100–200，价格在 140–160 附近上下移动 0.10，代表稀疏穿越。

每档先执行三次冷重建，再预热十对查询，最后执行默认 150 对比较。每对在同一个股票行锁下交替执行：

1. 全量读取该股票所有可索引规则，再用 Java 筛选。
2. 实际 RuleIndex.candidates 的 Redis 区间查询。

逐次断言候选 ID 集合相同。热查询时间排除股票锁等待和事务提交；基线包含全量数据库读取、对象映射和 Java 筛选。它衡量“全量读取改为区间候选”的差异，不是 Redis 与带合适联合索引的 MySQL 范围 SQL 的全面比较。

这里只测候选选择阶段，不把它冒充完整行情接口延迟。大量规则同时触发时仍需要状态更新、快照写入和 Outbox 写入，成本另外测量。

## 2. 真实 HTTP 请求

启动随机本地端口的 Spring Boot，使用真实 JWT 调用 /api/market/replay。每个请求只有一条行情，经过认证、参数校验、服务、MySQL 事务和 Redis 查询。

分别运行 1 个和 4 个请求线程；每线程对应一只股票，股票内按事件时间顺序发送。每股有 1000 条规则，行情不穿越阈值；预热 5 次后，每线程计时 100 次，最后核对数据库中的行情数量。

这是本机闭环负载下的观测吞吐，包含 HTTP、JWT 和事务开销；不是寻找饱和点的开放式恒定到达率压测，也不能换算为“支持多少用户”。

## 3. 真实 MQ 通知积压

让同一股票的默认 500 条规则在一次行情中全部触发：

1. 暂停本次消费组的消费者。
2. 在真实事务中创建触发事实与 Outbox。
3. 调用实际发布器，将所有任务发送到真实 Broker。
4. 确认此时还没有通知。
5. 恢复消费者，测量积压清空时间并核对 500 条通知。
6. 再向 Broker 发送 10 个相同业务负载，等待实际消费完成后确认通知数量不增加。

积压峰值指已触发但尚未生成通知的业务任务数，不是 Broker offset 的精确积压指标。端到端时间从数据库触发记录创建到通知创建，包含故意暂停消费和发布的时间；不能表示常态实时通知延迟。恢复后的消化速度单独记录，轮询精度为 50 ms。

## 4. 失败与恢复

| 场景 | 注入方法 | 核验结果 |
| --- | --- | --- |
| 消息发送失败 | 在发送调用处抛出异常，保持共享 Broker 正常运行 | 已提交 Outbox 保留为 FAILED；恢复发送后生成通知 |
| Broker 已接收但 Outbox 未确认 | 实际发送取得 SEND_OK 后，故意不标记 SENT | 租约到期后重发；两次实际消费仍只有一条通知 |
| Redis 不可用 | 停止并重新启动本次测试的临时 Redis | 行情事务回滚、最新价不推进；恢复后原事件重试成功，再次重试为 DUPLICATE |

前两项是确定性故障窗口模拟，没有杀死应用进程或使真实 Broker 宕机。第三项确实停止并重启了临时 Redis。测试 Redis 使用本次运行预留的固定映射端口，防止 Docker 重启时重新分配随机端口，干扰客户端恢复检查。

测试将发布租约缩短到 1 秒、初始退避缩短到 100 ms；日常默认分别为 30 秒和 2 秒。发布器由测试手动驱动，因此结果不包含正常定时扫描的额外等待。

Redis 故障策略依赖行情调用方保留失败事件并重试。系统不把未接受的行情伪装成成功，也不承诺调用方丢弃原事件后仍能恢复它。

## 运行指标

使用已有 Actuator/Micrometer，新增：

| 指标 | 含义 |
| --- | --- |
| pricepulse.rules.lookup | 候选查询耗时，包括发生时的重建成本；不包含股票锁等待 |
| pricepulse.rules.rebuild | 从 MySQL 重建单股索引的耗时 |
| pricepulse.rules.candidates | 成功查询返回的候选数量分布 |
| pricepulse.notification.deliveries，按 outcome 区分 | 消费尝试成功或失败次数 |

指标不按用户、股票或规则 ID 打标签，避免高基数。候选数不是已提交触发数；消费成功次数包含幂等重复投递，不是唯一通知数。业务正确性仍以数据库对账为准。当前没有默认扩大 Actuator 公开端点范围，也没有增加监控大屏或监控服务。

## 结果解读与边界

- 本机单应用、单 MySQL、单 Redis、单 Broker，未验证集群容错。
- MySQL 连接池为 5，消费者配置为 2–4 个线程；完整环境随报告保存。
- 每档 150 个样本的 P99 仅为本次观测值，不是稳定的生产 SLA。
- 冷重建只有三次样本，保留原始值，不推算冷启动 P99。
- 批量准备绕过 HTTP，不能宣称测出了规则创建接口吞吐。
- 重建仍是 O(N)，还会占用股票行锁并执行 Redis Lua；这是保留的优化方向。
- Broker 为 ASYNC_MASTER / ASYNC_FLUSH，SEND_OK 不等同于多副本强持久化，未做断电实验。
- 未覆盖长时间浸泡、热点单股饱和点、跨机网络、真实进程强杀、集群扩容和 DLQ 人工重放。
