# PricePulse 容量、周期与时间边界审计

审计日期：2026-11-02（Australia/Sydney）  
审计范围：当前 `price-pulse-once-only` 源码与公开配置；不把旧版压测结果当作当前一次性规则模型的容量承诺。

## 先回答最常问的两个问题

### 系统多久轮询一次？

系统并不是只有一个轮询周期：

| 场景 | 当前值 | 行为 |
| --- | ---: | --- |
| 行情与规则页面刷新 | 10 秒 | 仅页面可见时刷新当前时间线、规则和自选股价格；行情源本身不是 10 秒轮询，而是 WebSocket 实时推送 |
| 通知中心 | 正常 5 秒 | 单次请求 8 秒超时；失败后按 10／20／30 秒退避，最高 30 秒；页面隐藏时暂停，重新可见或窗口聚焦时立即刷新 |
| 个人监控订阅协调 | 5 秒 | 后端核对持久需求、上游 ACK、取消和名额释放；首次也是启动 5 秒后 |
| 行情故障持久化 | 1 秒 | 每秒尝试把内存中的连接／队列故障写入 MySQL；数据库失败时下一轮继续 |
| Outbox 发布 | 1 秒 fixed delay | 启动 1 秒后开始；一次运行完成后再等 1 秒，不是严格每秒整点执行 |
| 历史行情后台同步 | 5 分钟 | 应用启动时立即执行一次，之后每次执行完成后再等 5 分钟 |
| WebSocket 心跳 | 15 秒 | 15 秒一次 Ping；45 秒无有效接收或调度停顿／时钟漂移异常则重连 |
| 资产目录缓存 | 1 小时 | 搜索发现缓存过期才刷新；刷新失败至少等 30 秒再试 |

### 每个用户最多可以创建几条规则？

**当前没有规则数量硬上限。** `AlertRuleService.create` 不统计用户已有规则，也没有配额表或数据库约束。规则列表接口单次最多返回 100 条，只是读取上限，不是创建上限。因此当前用户可以持续创建超过 100 条规则，但普通列表只能看到最近的一部分，这既是容量风险，也是产品可用性问题。

建议上线前增加以下首版保护值：

| 建议项 | 建议初始值 | 计数口径 |
| --- | ---: | --- |
| 每用户 ACTIVE 规则 | 100 | 只计算仍等待目标价的一次性规则 |
| 每用户、每只股票 ACTIVE 规则 | 20 | 防止单一热门股票集中触发造成事务尖峰 |
| 每用户规则创建频率 | 10 次／分钟 | 创建、AI 草稿落库分别限流；不能用历史总数代替速率限制 |
| 每用户可监控股票 | 15（兼容起点） | 与现有十五股兼容范围一致；它不能防止单用户占满全局新代码名额，如产品强调多租户公平，应对新用户降到 5 或引入分层配额 |

这些是**防滥用的保守起始值，不是当前模型已经压测证明的容量**。上线后应根据 ACTIVE 规则分布、同价集中命中数、单股队列等待时间、MySQL 事务延迟和 Outbox 积压调整。

## 容量边界

### 用户、股票与监控订阅

| 项目 | 当前实现 | 性质与说明 |
| --- | ---: | --- |
| 用户总数 | 无上限 | 数据库自增主键；没有注册速率限制或业务配额 |
| 全局同时监控的去重股票 | 默认 15 | `market_subscription_control.symbol_limit`；数据库允许配置 1–10000，但当前 Alpaca 运行配置只接受最多 15 个支持的代码，不能仅改数据库就宣称可支持 10000 |
| 每用户监控股票 | 无独立上限 | 受全局去重预算间接限制；同一股票的多个用户共享一个上游订阅和一个全局名额 |
| 上游连接数 | 1 | 单个后端实例维护一条 Alpaca IEX WebSocket，不为每个用户建立连接 |
| 行情处理通道 | 每只股票 1 个线程 | 保证单股顺序；不同股票隔离。单只热门股票的处理能力无法通过增加用户数线性扩展 |
| 每股行情队列 | 默认 1024 | 配置校验范围 1–10000；满时丢弃不确定尾部、建立新 continuity，并立即生成队列故障事实，不静默扩大队列 |
| 行情 I/O 调度线程 | 3 | 用于连接、心跳、重连和历史同步；不包含每股处理线程 |

需要特别注意：“全局 15 个去重股票”不是“15 个用户”，也不是“每个用户 15 个独立上游订阅”。例如 100 个用户都监控 AAPL，只占 1 个上游股票名额，但会各自拥有规则和通知数据。

### 规则、触发与候选处理

| 项目 | 当前实现 | 性质与说明 |
| --- | ---: | --- |
| 每用户规则总数 | 无上限 | 包括 ACTIVE、COMPLETED、DELETED 均没有配额 |
| 每用户 ACTIVE 规则 | 无上限 | 当前最重要的缺口 |
| 每股规则数 | 无上限 | Redis ZSet 只保存 ACTIVE 候选，MySQL 是权威事实源 |
| 规则列表 | 默认 50，最大 100 | 单次返回上限，不是总量上限；当前没有 cursor，超过上限后无法从普通列表继续翻页 |
| 单规则触发历史 | 默认 100，最大 500 | 一次性模型正常只新增一次正式触发，但历史兼容数据仍可能更多 |
| 候选 MySQL 回查 | 每批 500 个 ID | 大量规则同价达到时会分批读取，但仍在同一笔行情事务内逐条完成规则和触发 |
| Outbox 事务内批量写 | 每批最多 500 条 | 只是减少 SQL 次数，不会合并业务事件；每个触发仍对应一条 Outbox |
| 价格上限 | 99,999,999,999.9999 | 正数、最多四位小数，由 `PriceTicks` 统一归一化 |
| 规则名称／备注 | 100／500 字符 | 请求与数据库一致 |

旧版候选索引实验覆盖过 1,000、10,000、50,000 条规则和 100,000 笔固定行情，但它使用旧规则状态分布，且只证明候选集合与选择层特征。当前一次性规则模型已明确撤下旧容量 harness，因此不能回答“当前系统稳定支持多少总规则／多少 QPS”；必须重新压测。

### 请求与字段边界

| 项目 | 当前实现 | 说明 |
| --- | ---: | --- |
| 公共股票搜索 | query 最长 64；limit 1–100 | 前端固定取 50 条 |
| Alpaca 资产搜索 | query 1–64；limit 1–50 | 前端固定取 20 条；一次目录响应超过 100,000 个资产会被拒绝 |
| 注册邮箱／显示名 | 254／64 字符 | 邮箱全局唯一 |
| 注册密码 | 8–72 字符且不超过 72 UTF-8 字节 | BCrypt 输入边界；登录接口本身没有独立长度注解或速率限制 |
| AI 自然语言输入 | 最长 1,000 字符 | 只生成草稿，不直接保存规则；没有用户级调用配额 |
| 事件 key／来源 | 128／32 字符 | 正式外部写入口已由安全配置拒绝，正常 REAL 行情只走内部接入 |

这些字段长度能限制单行数据大小，但不能代替请求体总大小、并发数和调用速率限制。

### 历史准备、时间线与模拟

| 项目 | 当前实现 | 性质与说明 |
| --- | ---: | --- |
| 显式历史准备工作线程 | 2 | 固定 2 个工作线程 |
| 历史准备等待队列 | 32 | 队列满返回“历史准备繁忙” |
| 内存 job 表 | 最多 256 个股票 job | 同一股票跨用户合并为一个 job；达到 256 拒绝新请求 |
| READY／FAILED job 复用 | 5 分钟 | 5 分钟内返回原结果；完成 10 分钟后才从内存表移除 |
| PENDING job 超时 | **未设置** | PENDING 永远不会被清理；若外部下载永久卡住，会长期占 job 和工作线程，是需要修复的缺口 |
| 自动历史同步范围 | 约 1 个月 + 8 天 | 按纽约时区计算，每 5 分钟同步；每批最多 15 只股票 |
| 图表窗口 | 1H／当日／7 天／1 个月 | 1D 从当日开盘到收盘；1W、1M 使用纽约日历时间 |
| 正式事件查询范围 | 最长 40 天 | 每页 100 条，使用固定 watermark cursor |
| 模拟实验数 | 每用户 1 个 | 数据库唯一约束；明确开始新实验会事务内删除旧实验及其步骤／事件后替换 |
| 模拟推进 | 每批最多 60 个点 | 当前正常推进生成 60 个交易分钟；开盘跳空首批可为 1 个点 |
| 模拟价格分页 | 10 个批次／页 | 每批最多 60 点，因此通常最多约 600 个模拟点／页；前端会继续读取 cursor 直到完整 |
| 模拟事件分页 | 100 条／页 | 固定 watermark，避免翻页期间新事件改变已读页 |
| 自动播放间隔 | 默认 2 秒 | 用户可选 1／2／5 秒；表示每隔多久请求推进一批，不表示模拟市场的一分钟真实等待 |

### 通知与消息投递

| 项目 | 当前实现 | 性质与说明 |
| --- | ---: | --- |
| Outbox 领取批次 | 50 条 | 一次调度最多 4 批，即名义上最多领取 200 条；逐条同步发 MQ，实际吞吐取决于 Broker 延迟，不能写成稳定 200 条／秒 |
| Outbox 最大尝试 | 8 次 | 失败退避为 2、4、8、16、32、64、120、120 秒；达到 8 次后保持 FAILED，不再自动领取 |
| Outbox 租约 | 30 秒 | SENDING 超过租约可由后续调度恢复；发送成功但本地确认失败时允许重复投递 |
| MQ 消费线程 | 初始 2，最多 4 | RocketMQ 最大重消费 3 次；数据库唯一约束保证重复消息不产生重复通知 |
| 通知 feed | 最新 20 条 + 总数／未读数 | 前端每 5 秒读一次 |
| 通知列表 | 默认 50，最大 100 | 当前没有 cursor；超过 100 条后只能看到有限窗口 |
| Toast | 最多同时 3 个，显示 6 秒 | 多条新通知会合并；这是 UI 行为，不是通知存储上限 |

Outbox 的端到端送达时间没有固定 SLA。正常空闲时通常由“下一个约 1 秒发布周期 + MQ + 消费事务”组成；故障时会受到退避、30 秒租约、Broker 和数据库可用性影响。

## 超时、有效期与故障时间线

### 外部调用和认证

| 项目 | 当前值 |
| --- | ---: |
| Alpaca REST 连接超时 | 10 秒 |
| Alpaca REST 单请求超时 | 25 秒 |
| Alpaca WebSocket 连接超时 | 10 秒 |
| WebSocket 认证／订阅握手超时 | 12 秒 |
| 动态订阅 ACK 超时 | 12 秒 |
| AI 连接／读取超时 | 10／45 秒 |
| JWT access token | 2 小时 |
| Spring graceful shutdown phase | 10 秒 |
| WebSocket Close 等待 | 发送后 3 秒超时，应用最多等待约 4 秒 |

当前只有 access token，没有 refresh token、服务端撤销列表或真正的 logout 失效机制；前端退出只能删除本地 token，已签发 token 最长仍可使用到 2 小时到期。

### 行情新鲜度与重连

| 项目 | 当前值／规则 |
| --- | --- |
| 正式成交最大年龄 | 2 分钟；更旧成交持久化为丢弃，不参与正式价格和规则判断 |
| 允许未来时钟偏差 | 30 秒；更未来的成交丢弃 |
| 页面“近期成交” | 开市时最后观察成交不早于 2 分钟前，否则显示延迟 |
| 心跳周期／静默门槛 | 15／45 秒 |
| 客户端时钟漂移门槛 | 正负 5 秒；调度长暂停或墙钟跳变按连续性故障处理 |
| 重连退避 | 1、2、4、8、16、32、60 秒，另加 0–249 ms 抖动；稳定订阅 30 秒后失败计数归零 |
| 连接中断告警 | 故障持续达到 30 秒才产生中断意图；5 或 29 秒内恢复不告警 |
| 队列溢出告警 | 一旦确认实际丢弃就立即产生，不等待 30 秒 |
| 故障检查 | 每 1 秒；所以“30 秒”是业务门槛，不承诺第 30.000 秒送达通知 |

## 数据保留现状

当前业务表基本都是**无限期保留**，没有定时清理或归档任务：

- 规则删除是 `DELETED` 逻辑删除；规则、触发快照和通知继续保留。
- `quote_events`、分钟历史、触发、通知、SENT／FAILED Outbox、监控故障都没有 TTL。
- 取消个人股票监控会保留订阅行，只把需求状态改掉；相关规则被逻辑删除。
- Redis 规则候选索引 TTL 是 24 小时；过期或 token 不匹配时从 MySQL 重建，因此 Redis 不是历史事实存储。
- WebSocket 最近失败诊断只在内存保留最近 20 条；进程重启后不保留这 20 条诊断队列。
- 每用户只保留一个模拟实验；新实验物理删除旧实验，并通过外键级联删除旧步骤、规则快照和事件。

无限期保留意味着容量最终由数据库增长决定，而不是接口的 `limit` 参数决定。上线前至少要为 `quote_events`、已发送 Outbox、已读通知和监控故障确定在线保留期、归档策略、删除批次和恢复要求；不能直接写一个大 `DELETE` 定时任务而不验证外键和审计需求。

## 当前没有定义的关键边界

以下项目在公开配置和业务代码中没有明确值：

1. 每用户 ACTIVE／历史规则上限、规则创建速率。
2. 每用户监控股票上限；现状只有共享的全局预算。
3. 注册、登录、AI 草稿以及普通 REST API 的速率限制。
4. HTTP 请求体上限、全局并发请求数、Web 容器线程数。
5. MySQL 连接池大小、连接／查询超时和慢查询预算。
6. Redis 连接池与命令超时、RocketMQ 同步发送超时的项目级配置。
7. quote、通知、Outbox、故障与历史分钟数据的在线保留期。
8. 当前一次性规则模型的总规则容量、每股持续成交吞吐、端到端 P95／P99 和积压恢复时间目标。
9. PENDING 历史准备任务的执行超时与取消机制。
10. 规则列表、通知列表的完整 cursor 分页；当前只有返回数量上限。

## 建议的落地顺序

1. **先补业务配额和分页：** 100 ACTIVE／用户、20 ACTIVE／用户／股票、15 监控股票／用户；在同一数据库事务中计数并拒绝，避免只靠前端。规则和通知列表增加稳定 cursor。
2. **再补入口保护：** 注册、登录、AI、规则创建的用户／IP 限流；历史下载已有单 HTTP 请求 25 秒超时，但仍应增加 60 秒整体 job 截止、取消和可恢复状态。
3. **定义数据生命周期：** 先按表记录日增长、外键关系和恢复要求，再决定在线保留／归档。通知和规则历史属于用户事实，不能与可重建 Redis 索引采用同一种清理策略。
4. **重新做当前模型容量测试：** 至少覆盖 15 股、每用户 100 ACTIVE、单股规则集中同价达到、正常稀疏命中、Redis 冷重建、Broker 故障与恢复积压；同时报告丢弃数、队列最老等待、MySQL 事务、Outbox backlog 和端到端延迟。
5. **最后给 SLA：** 在未完成上述测试前，只能描述机制和已配置时间，不能承诺“支持 50,000 条当前规则”或“通知 1 秒必达”。
