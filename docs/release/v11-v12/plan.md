发布顺序：

1. 完成安全扫描和本地关键回归，普通推送发布分支，创建面向 main 的 PR。
2. 核对 diff、全部提交、评审／保护要求及固定 head 的 CI。CI 未成功、存在不可控自动部署或未解决审查要求时，不合并。
3. 使用 expected head SHA 合并，保留 merge commit；记录 GitHub main 的完整合并 SHA。
4. 重新取得该 main 提交，在隔离构建目录冻结源码；核对业务／前端／迁移树与候选一致，再构建 JAR、前端 dist 与 SHA-256 清单。构建不覆盖原 `target/classes`，不带私人 application-local.yml。
5. 正式运行只能使用上述 main 构建。PR 状态及本机发布清单记录实际合并 SHA／构建 hash，不用未经核对的副本替换。

## 等待单独批准的维护步骤

预留 5–10 分钟；不是零停机承诺。最终备份体积、DDL 锁及上游确认可能延长窗口。维护期间不提交页面业务操作。

1. 重新核对原进程身份、18081 监听者、数据／Outbox／MQ、全部规则门禁、私人配置及候选指纹。明确授权后仅平稳停止原后端；确认进程和监听均退出，保留原关闭诊断。不能在旧接入仍活着时启动新版或探针。
2. 旧进程退出后生成**新的最终截止点**一致性 SQL、清单与 hash，再隔离恢复验证。不沿用本轮运行中预备快照作为最终恢复点。
3. 用独立 Flyway 过程迁移 V11，再 V12；只连接本机指定正式库，不启动 Spring、IEX 或 MQ。保持 V1–V11 checksum，包含既有 db/local repeatable 位置。每步核对原行／列（V12 仅排除恒定模式／rearm 两列），最后 validate 与重复迁移 0 次。失败保持新应用未启动，不盲目 repair／改脚本。
4. 从固定 main 的 JAR 启动唯一后端，沿用原 JDK 与私人配置／环境。JAR 不包含私人 local 文件，须显式加载原外部 local 配置并启用 local profile；保留正式写入 true、动态订阅原开关、原 Topic／消费组和 15 名额。先检查配置解析结果，缺凭据／地址不匹配即不启动，不打印值。
5. 仅在批准的前端切换步骤中停止旧 Vite，启用同一 main 的已构建前端及既有 `/api` 代理。不得通过提前切换原源码让旧 Vite 自动载入新版。
6. 记录 main SHA、JAR／dist hash、PID、启动时间、唯一监听者、Flyway V12 与校验结果；比对所有历史、规则、通知和模拟事实。读 API 检查旧模拟 `generatorSupported=false`，不为验收覆盖实验、创建近价真实规则、取消他人需求或标记通知已读。
7. 观察至少 90 秒心跳、当前连接／intent 的 15 股实际 ACK、Outbox／MQ 和故障状态；无成交只说明休市，不能作自然成交／提醒验收。

启动后 ACTIVE 目标若被**下一笔可信价格**满足，可能正常完成并通知；恢复首笔不再一概要求零触发。不会根据休市旧价或历史缓存提前补发；RECOVERY 采用实际确认时间，不能虚构缺口内突破。

## 已演练的回滚边界

- 本轮已验证的是：把真实 V10 备份恢复到另一空 schema，全部原数据／DDL／Flyway 匹配；未在正式库执行切库，未声称已经做过生产回滚。
- 迁移后、**新版尚未写入任何新事实**时，可在批准的维护范围内将最终截止点 SQL 恢复到新的空本机库并验证，保留失败 V12 库，指向已保全的准确 V10 构建／配置。新实例必须完全停止后才恢复唯一旧实例；不删除新表、不清 MQ、不恢复／重置消费偏移、不清共享 Redis。
- 一旦产生 V12 规则修改／触发、监控中断意图、通知或新模拟事实，不能用旧备份覆盖，也不能仅替换 JAR。先保存失败版本新事实与 MQ 状态，优先向前修复；如需兼容回退／迁移新事实，另行评审并批准。旧 V10 消费者不能安全处理已经产生的监控消息。
- MySQL 多条 DDL 不具备整段回滚；V12 删除字段后旧二进制不兼容。备份不完整、恢复失败、数据不匹配、上游连接未退出等情况均停止危险操作。
