# Phase 4：Redis 规则索引、穿越匹配与状态机

状态：**已完成（2026-10-26）**。

## 已实现的业务闭环

创建提醒规则后，实时行情、历史回放和模拟行情都会进入同一匹配引擎。引擎只选取价格变化区间内的候选规则，由 MySQL 再检查规则当前状态与阈值。每次真正触发会更新规则状态，保存不可变的触发快照，并创建一条 `PENDING` Outbox。

Phase 5 将实现 Outbox 发布、RocketMQ 消费和站内通知。因此当前可以查到触发历史，Outbox 会保留待发送任务；用户通知尚未生成。

## 价格与规则语义

| 情况 | 判定 | 结果 |
| --- | --- | --- |
| 第一次接受某股票行情 | `latest_quote_at` 为空 | 仅建立基线，不依据演示种子价格推断穿越 |
| 上破 | `旧价 < 阈值 <= 新价` | 触发有效的 `ABOVE` 规则 |
| 下破 | `新价 <= 阈值 < 旧价` | 触发有效的 `BELOW` 规则 |
| 价格不变 | `旧价 = 新价` | 不触发，不重新激活 |
| 上破规则重新激活 | 冷却时价格下降到 `新价 <= rearmPrice` | `COOLDOWN → ACTIVE` |
| 下破规则重新激活 | 冷却时价格上涨到 `新价 >= rearmPrice` | `COOLDOWN → ACTIVE` |

例如上破阈值为 100、重新激活价为 95：`94 → 100` 触发，`100 → 99 → 101` 不再触发，`101 → 95` 重新激活，之后 `95 → 100` 才能再次触发。

状态流转：

```text
ONCE:    ACTIVE ──穿越──> COMPLETED
REPEAT:  ACTIVE ──穿越──> COOLDOWN ──回到重新激活价──> ACTIVE
管理:    ACTIVE / COOLDOWN ──暂停──> PAUSED ──手动恢复──> ACTIVE
删除:    任意未删除状态 ──删除──> DELETED
```

- 手动恢复明确开启新的 `ACTIVE` 监控周期，不在恢复请求内补发历史提醒；之后仍必须发生真实穿越。
- 仅 `ACTIVE` 或 `PAUSED` 可修改。修改时清空 `last_triggered_at`，已有触发记录保留原规则快照。
- 暂停、修改、删除从事务提交后生效；与其并发的行情按股票行锁的先后顺序处理。暂停提交前已经完成的触发不撤销。
- 行情触发和重新激活也会增加规则 `version`；用户提交过期版本时返回 409，需要刷新后再修改。
- 所有价格大于 0，最多 4 位小数，上限 `99999999999.9999`。这一统一边界保证 Redis 整数分值精确，不会发生跨区间或浮点舍入。
- 行情时间统一截断到微秒，与 MySQL `DATETIME(6)` 一致，精度更细的原始请求也可安全重试。

## ZSet 索引结构

每只股票使用一个 ZSet：`pricepulse:rules:{stockId}`。规则 ID 是 member，价格乘以 10000 转为整数 tick 后作为分值。通过四个互不重叠的分值区间，区分触发方向与重新激活方向。

| 分值区间 | 内容 | 查询时机 |
| --- | --- | --- |
| `0 × 10^15 + thresholdTick` | `ACTIVE / ABOVE` | 价格上涨，查 `(旧价, 新价]` |
| `1 × 10^15 + thresholdTick` | `ACTIVE / BELOW` | 价格下跌，查 `[新价, 旧价)` |
| `2 × 10^15 + rearmTick` | `COOLDOWN / ABOVE` | 价格下跌，查 `[新价, 旧价)` |
| `3 × 10^15 + rearmTick` | `COOLDOWN / BELOW` | 价格上涨，查 `(旧价, 新价]` |

所有分值均小于 `2^52`，可由 Redis double 精确表示。一次价格变化最多查询两个区间，热路径不全量遍历该股票的规则。MySQL 对候选 ID 分批读取，再次检查股票归属、状态和实际阈值，过期的多余候选不会生成错误提醒。

单 ZSet 同时包含分值为 `-1` 的版本标记 `@<token>`。这样缓存键被淘汰时，标记与索引一起消失，不会出现“标记仍在、某个方向索引已丢”的假完整状态。

## 规则修改、索引同步与重建

Flyway `V3` 为 `stocks` 增加 `rule_index_token`。每次规则创建、修改、暂停、恢复、删除或匹配状态变化，都在同一个股票锁内将 token 换为新的 UUID。

1. 行情先锁股票，读取数据库 token。
2. Redis Lua 在同一操作内校验 token 并查询区间。
3. 缓存缺失或 token 不一致时，从该股票的 MySQL `ACTIVE / COOLDOWN` 规则原子重建，再查询。
4. 状态变化后，Lua 校验旧 token，只增量更新本次变化的规则，并替换为新 token。

Lua 写入时先移除旧标记，完整更新后才写新标记；即使脚本执行中途报错，也不会把半成品索引标记为有效。

选择 UUID 而非简单自增版本，是为了处理“Redis 更新成功，但 MySQL 事务随后回滚”的情况。回滚后的缓存 token 永远不会被后续事务复用，下一次查询一定能发现不一致并重建。

规则跨股票修改时，按股票 ID 从小到大锁定原股票与目标股票，再重新检查规则版本与归属，避免死锁及并发移股造成的漏同步。相关事务使用 `READ_COMMITTED`，保证加锁后读取最新已提交规则。

正常路径是区间查询与候选增量更新。冷启动、键过期或恢复重建需要读取该股票全部有效规则，成本为 O(N)，大规模重建的停顿与内存占用将在 Phase 7 测量。

## Redis 故障策略

- 规则管理时，Redis 增量同步失败不会撤销已保存的规则。数据库新 token 与旧缓存不一致，恢复后会自动重建。
- 行情匹配时，Redis 查询失败返回 503，并回滚本次行情记录、最新价、规则状态、触发记录和 Outbox。调用方应保留原事件并使用相同 `eventKey` 重试。
- 缓存错误不能被当成“零条候选”。当前没有 MySQL 区间查询降级，也不宣称在调用方未重试的情况下仍能接收行情。

## 触发事务与历史查询

一条被接受的行情，其以下数据在同一 MySQL 事务内提交：

```text
行情记录与处理结果
    + 股票最新价
    + 规则状态与版本
    + alert_triggers 规则快照
    + outbox_events PENDING 任务
```

触发唯一键为 `rule:{ruleId}:version:{触发前版本}`。重复行情在匹配前被拦截，并发事件通过股票锁与条件更新保证一致性。Outbox 包含 `schemaVersion=1`、triggerId、userId、ruleId 与 stockId，事件类型为 `ALERT_TRIGGERED`。

新增接口 `GET /api/alert-rules/{ruleId}/triggers?limit=100`，要求 JWT。查询同时约束当前用户 ID；不属于自己的规则返回空列表，自己已删除规则的历史仍可查看。行情响应新增 `matching`，包含候选数量、触发数量与重新激活数量，重复或丢弃行情不再次匹配。

行情实验台扩展：`POST /api/market/simulate` 和单股票 `/replay` 可选传入 `ruleId`。只有属于当前用户及目标股票的规则才允许观察；有效点的 `observation` 返回匹配前后状态、实际规则阈值、`TRIGGERED / REARMED / NONE`、版本和真实触发 ID。观察读数与匹配共享股票行锁及事务，不根据前端价格穿越推测是否触发。没有选择规则、重复或丢弃行情时，`observation=null`。不指定规则的原有调用方式保持不变。
