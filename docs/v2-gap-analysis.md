## 1. 总体判断

V1 的业务处理核心可以复用：模块化单体、规则状态机、Redis 候选索引与版本重建、事务内触发快照与 Outbox、MQ 重试及消费幂等、用户认证均已存在。

V2 属于跨模块的增量升级。主要工作集中在：

1. 将按股票共享的行情状态扩展为按真实环境／模拟实验隔离的业务状态。
2. 建立按时间范围查询价格与全部触发事件的只读时间线。
3. 新增真实行情连接、订阅恢复和数据健康管理。
4. 将一次性批量模拟扩展为有持久化进度的逐小时实验。

**当前尚无一个 V2 阶段满足完整验收条件。** 已有的图表和实验展示属于 P0 的基础能力，不等于已完成 V2 统一时间线。隔离设计应先于 P0 接口定稿；真实行情接入必须在隔离验收之后。

## 3. 隔离是最重要的结构性差距

### 3.1 当前共享状态的具体位置

| 位置 | 当前行为 | 对 V2 的影响 |
| --- | --- | --- |
| `stocks.latest_price / latest_quote_at / rule_index_token` | 每只股票只有一份最新价、处理水位和索引版本 | 同股票无法同时承载真实流与两个独立实验 |
| `QuoteIngestionService.ingest` | 按 `stockId` 锁股票，匹配后更新这份最新价 | 模拟／回放与未来真实接入会争用并改变同一业务状态 |
| `AlertEvaluationService.evaluate` | 依据股票索引查询该股票全部候选规则 | 选择观察某条 `ruleId` 不会限制实际匹配范围；其他用户的同股规则仍参与匹配 |
| `RuleIndex.key` | Redis Key 为 `pricepulse:rules:{stockId}` | 实验之间共享候选集合及索引版本；只改 Key 也不能隔离 MySQL 状态 |
| `quote_events` | `event_key` 全局唯一，查询仅按股票 | 相同业务事件键跨实验可能冲突；查询不能识别私有实验 |
| `alert_rules / alert_triggers / notifications` | 没有环境／实验上下文 | 规则状态、历史及通知无法按 V2 要求隔离与授权 |
| 通知 `feed / read-all` | 按用户统计／修改全部通知 | 加上环境筛选后还需同步限定计数、批量已读及轮询基线 |

- [行情事务](../src/main/java/com/ezra/pricepulse/market/QuoteIngestionService.java#L54)、[候选规则匹配](../src/main/java/com/ezra/pricepulse/alert/AlertEvaluationService.java#L39)。

### 3.2 建议明确的模型职责

以下是建模方向，不是已确定的 DDL：

- **股票目录**：保留股票代码、名称、交易市场与币种等共同信息。
- **行情作用域／流状态**：用真实环境或模拟实验唯一确定一份行情流，保存其最新价、水位、索引版本；对应行锁以该流为粒度。
- **模拟实验**：关联用户、模拟时钟、配置、种子、状态和批次进度。
- **模拟批次**：明确实验 ID、批次序号、覆盖时间、幂等键、处理结果；可用独立表或经过验证的等价持久化设计。
- 规则、事件、触发和通知要能通过不可变关系追溯到正确作用域，并在入口与查询处校验访问权。

不需要在每张表机械地重复所有环境字段；需要保证作用域链路不可歧义、授权可检查、查询有效率。Redis Key、事件去重键及数据库索引必须随作用域一起审查。全局主键可继续复用，不应无理由地重做所有唯一键。

现有股票行锁用于保证匹配与规则修改一致性，这个机制值得保留，但锁定对象及索引版本要迁移到独立行情流，避免同股票的不同实验共享状态。Outbox 与 MQ 物理服务可以继续共用。

### 3.3 V1 数据迁移需要专门方案

已有演示数据没有真实市场的来源和授权证明，应保留在明确的历史演示／模拟域。V1 行情由多用户共享，不能直接凭股票或规则用户给全部旧行情分配一个新的私有实验。

建议先设计 legacy 数据映射或只读归档，再决定是否复制为用户实验。必须核对旧触发快照、通知、未发布 Outbox 和重试消息的关联，不把迁移变成二次业务触发。若消息结构变更，要覆盖旧 `schemaVersion=1` 的待处理消息兼容性。

## 4. 图表与查询：已有组件可扩展，数据契约需要升级

### 已有基础

- `PriceSparkline` 提供价格刻度、准星、触发／重新激活节点与标签、冷却区间和方向键操作。
- `DashboardView` 用 `quoteEventId` 对齐实际触发记录；历史方向和阈值读取触发快照。
- `SimulationResults` 使用本次完整响应，最多可绘制请求上限的 1000 个有效点。
- 快速切换股票／规则已有请求版本或中止保护，可以复用到时间窗口／作用域切换。

### 与任务书不一致的部分

1. **X 坐标仍按数组下标等距计算。** 即使刻度显示时间，也不按实际经过的时长定位；同秒行情会降级为点序号。V2 要按事件时间映射，并统一 UTC 时刻与市场时区显示。[代码](../frontend/src/components/PriceSparkline.vue#L51)
2. **没有 1H / 1D / 1W / 1M 查询。** 目前前端读取最近 100 条行情，后端只支持 `stockId + limit`，没有时间边界、交易日或作用域。[接口](../src/main/java/com/ezra/pricepulse/market/MarketController.java#L46)、[SQL](../src/main/resources/com/ezra/pricepulse/market/QuoteEventMapper.xml#L32)
3. **当前一次只选一条图上规则。** 尚不支持默认最多三条阈值线，以及独立于阈值筛选的全部历史事件图层。[代码](../frontend/src/views/DashboardView.vue#L35)
4. **事件依赖当前窗口里的原始报价 ID。** 没有对应点就不画标记。V2 使用时间窗口和曲线采样时，事件应按自身时间与触发价定位，不能因为曲线被采样就丢失。[代码](../frontend/src/views/DashboardView.vue#L45)
5. **有标签避让，没有事件聚合展开。** 隐藏放不下的文字标签与保留可检索的聚合事件是不同能力。[代码](../frontend/src/components/PriceSparkline.vue#L97)
6. **信息仍是图内浮框。** 没有固定信息栏、横纵轴悬停数值标签；点击事件只切换当前点，未提供完整快照与通知状态详情。[代码](../frontend/src/components/PriceSparkline.vue#L226)
7. **删除历史尚无完整 UI 入口。** 已完成规则仍可在列表选择；已删除规则被当前规则列表排除，触发历史接口本身保留记录。新时间线要从持久化事件查询，不依赖当前规则是否还出现在列表中。
8. **数据健康状态缺失。** 当前只有最后行情时间，没有连接中、延迟、断线、休市与缺口提示。股票行情页面也没有持续刷新机制；现有 5 秒轮询针对通知，不会自动刷新股票曲线。

建议先定义只读时间线契约，包含：股票、作用域／实验、时间范围、显示时区、行情点、事件、可选阈值及数据健康状态。曲线可按时间桶聚合／采样；触发事件需要独立完整查询、分页或聚合展开，不能用一个固定 `limit` 静默截断。通知未生成、已生成未读、已读应分别表达，不能用 Outbox `SENT` 推断用户通知已创建。

P0 可用适配器把 V1 数据映射到明确的 legacy 模拟域，先实现只读查询与图表；P1 落地隔离后复用同一契约。已有 `GET history` 是只读的，可以保留；未来供应商历史补图不能调用会执行业务匹配的 `/replay`。

## 5. 真实行情：处理引擎有基础，接入与恢复尚未实现

代码中未发现真实行情供应商、WebSocket 订阅管理、交易日历或健康状态模块。目前只预置三只 `DEMO` 股票。[种子数据](../src/main/resources/db/local/R__seed_demo_stocks.sql)

可复用的处理能力包括规范化、价格精度、事件去重、未来／过期／乱序处理、串行事务和实际规则匹配。新增范围至少包括：

- 服务端数据源适配、连接认证、初次订阅、退避重连、订阅恢复及关闭。
- 供应商成交事件与条件筛选、可诊断的丢弃原因、断线缺口与最后有效事件时间。
- 只读历史查询／缓存路径与实时规则处理路径的职责分离。
- 行情源状态及市场时区／交易时段查询。
- 从服务端存储到浏览器的持续更新机制；供应商 WebSocket 不会自动使现有 Vue 页面更新。首版可以评估轻量轮询或现有技术适合的推送方式。
- 对真实行情写入口的授权边界。目前 `/quotes / replay / simulate` 都只要求登录，V2 需确保普通用户的实验操作不能写入真实行情域。

接入前需验证的条件：

1. Alpaca 对应账户的 feed、可订阅数量、历史范围、费用、数据许可和自动提醒用途是否允许。本次没有检查外部账户或供应商条款，不判断已具备接入资格。
2. 供应商时刻的时区和精度。当前入库截为微秒，并以 `eventTime <= latestQuoteAt` 丢弃事件；若供应商存在相同时刻的不同有效成交，需要制定时间／序号排序策略。
3. 断线跨过价格阈值后，是继续从上一笔有效价判断还是建立新基线；这影响提醒语义，不能通过补画历史曲线悄悄决定。
4. 现有处理按同股串行，数据接收速率和数据库成本要实测，明确有限缓冲、顺序与过载策略。

首批 3–5 只股票的范围有利于控制工作量，现阶段没有证据要求替换框架或拆分微服务。

## 6. 模拟器：缺少独立时间和可恢复的实验进度

当前 `MarketService.simulate` 一次同步生成全部事件；每步时间为 `startTime + index × 1 微秒`。1000 步仅推进 1 毫秒。前端每次使用浏览器本地当前时间作为起点，运行后生成新 `runKey`，结果保存在页面内存。[后端](../src/main/java/com/ezra/pricepulse/market/MarketService.java#L68)、[前端](../frontend/src/views/SimulationView.vue#L103)

需要新增：

- 实验的持久化创建、用户归属、状态、模拟时钟及历史查询。
- 每小时内多条事件的确定性时间和价格生成；跨批次延续相同实验的种子／生成进度，而不是每次重新初始化随机序列。
- 持久化批次序号、幂等键和处理结果，处理双击、重试、两个浏览器同时推进及进程恢复。
- 前端单一调度循环：等待上批确认后再提交下一批；播放速度仅调整批次间真实等待时间。
- 暂停语义：建议停止提交新批次，已受理批次的结果正常收齐，明确展示暂停生效位置。
- 回看只查询旧数据；重新开始创建新实验，不覆盖旧水位或通知。

当前 `ruleId` 是一次请求中的观察对象，不是模拟实验身份。`RuleObservation` 返回实际状态变化很有价值，但重新激活轨迹目前没有持久化；刷新后只能恢复已有触发记录。若继续保留 V1 的完整冷却轨迹体验，需要持久化转换记录或等价的批次观察结果，不应根据当前规则配置推演历史。

## 7. 通知与可用性

通知生成、用户隔离、准确未读计数、全部已读、前后台轮询与旧请求防护均可复用。V2 需要把作用域带入列表、计数、批量已读、缓存基线及请求版本；切换环境／实验时也要清理旧作用域的响应与提示。

目前通知行点击用于标记已读，弹窗点击进入通知列表，尚无定位股票和触发时间的导航。[通知页](../frontend/src/views/NotificationsView.vue#L80)、[弹窗](../frontend/src/components/NotificationToasts.vue#L8)

建议为定位事件提供独立入口，携带稳定的触发 ID 及作用域；只读打开图表不执行模拟、回放或发送通知。模拟通知需要明显标识。规则表单已校验重新激活价的大小关系，仍需生成方向与价格对应的动态示例。

AI 草稿保留现有流程，只补当前作用域的合法股票／规则保存上下文兼容，不能由模型决定实验访问权限。

## 8. 实施顺序、范围与门槛

| 阶段 | 主要改动 | 数据库／接口影响 | 最低验收门槛 |
| --- | --- | --- | --- |
| P0 前置设计 | 明确作用域、时间语义、只读时间线与事件完整性契约，固定当前 V1 基线 | 设计迁移和 DTO，不急于实施全部隔离 | 后续 P1 可沿用查询上下文；不会把 V1 演示域伪装成 REAL |
| P0 统一图表 | 时间比例、窗口、固定信息栏、轴高亮、多规则、聚合详情与独立事件层 | 新只读时间线／事件查询；可先适配 V1 | 至少两条方向不同的历史事件准确展示；窗口与回看不增加触发／通知；快速切换不串结果 |
| P1 环境隔离 | 流状态、实验归属、索引／版本／幂等作用域、读写授权、迁移 | 跨模块迁移及 SQL／DTO／消息上下文调整 | 同股 REAL + 两实验并行，价格／状态／索引／历史／通知互不影响，跨实验越权和相同事件键测试通过 |
| P2 真实接入 | 供应商适配、历史只读路径、WebSocket 恢复、健康状态、浏览器更新 | 数据源配置与状态查询；不必替换可靠消息机制 | 授权与数据口径确认，真实事件可查，断线重连／恢复订阅与去重有证据 |
| P3 模拟推进 | 独立时钟、持久化批次、下一小时、播放／暂停／继续、历史回看 | 实验与批次接口及查询；复用既有匹配引擎 | 三小时连续推进、暂停、同批重试、并发推进及恢复不重复执行；回看无业务副作用 |
| P4 整体验收 | 全链路回归、交叉隔离、故障与性能对照、文档演示 | 以修复验收问题为主 | 核心链路、迁移、隔离、恢复与同条件性能结果完整保存 |

工作量判断：P1 是改动最广、最应优先设计的阶段；P0 为中等规模前后端增量；P2 有明显供应商外部不确定性；P3 的主要工作是可靠的批次状态管理。P2/P3 都依赖 P1，按任务书顺序进入实施。

## 10. 开始编码前应固定的细节

- REAL 流与用户模拟实验的作用域模型，以及 V1 演示数据的迁移／归档方式。
- UTC 存储与市场时区显示契约；1D 按最近交易日，其他窗口的自然时长／交易时长及盘前盘后范围。
- 曲线采样粒度与全部事件检索方式；默认三条阈值线不限制历史事件图层。
- 断线跨缺口后的提醒基线策略；历史补图始终不触发业务。
- 模拟一小时内的事件频率、批次重试结果、暂停和继续的精确定义。
- 供应商实际账户可用的 feed／历史与数据许可。此项需要外部验证，不能根据需求文档推定已具备。

上述细节应形成 P0 简短实施方案与接口契约，再分阶段开发。当前无需更换 Spring Boot、MyBatis、Vue、Redis 或 RocketMQ。
