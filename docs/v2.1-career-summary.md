# PricePulse V2.1：Java 后端求职与面试总结

2026-10-30 封版材料。指标来自已执行测试，不将合成输入写成实际市场容量。正式加载与自然行情观察见 [交付记录](v2.1-final-delivery.md)，设计细节见 [最终架构](v2.1-final-architecture.md)。

## 项目简介（100 字以内）

PricePulse美股实时提醒系统，基于Spring Boot、Redis区间匹配、MySQL事务与RocketMQ幂等通知，支持多用户共享行情订阅和隔离的开盘跳空模拟。

技术栈：Java 21、Spring Boot 3.5、MyBatis、MySQL 8.4、Redis 7、RocketMQ 5.3、Spring Security／JWT、Spring AI、Vue 3／TypeScript。编译目标 Java 21，记录的本机测试与基准运行 JDK 为 25。

## 建议写进简历的四个亮点

以下表述可按岗位篇幅选三至四条；性能限定词应保留。

1. **规则匹配与可重建索引**：实现 Redis ZSet 四分段候选索引、Lua token 校验与失效重建。完成 1000–50000 规则三方案及 10 万笔固定回放，候选集合零差异；相对逐笔 MySQL 范围查询，规则 SELECT 减少 21.04%，加入同价 SQL 短路后额外减少仅 1.31%。Redis＋回查选择层累计 58.908 s，对照为 39.861 s；不宣称完整处理加速。[新实验与原始数据](performance/v2.1-rule-selection-2026-10-31/report.md)
2. **事务提醒与可靠通知**：将规则状态、真实触发快照及 Outbox 同事务提交，采用租约领取、失败退避与 RocketMQ 至少一次投递；消费者核对持久触发并以唯一约束幂等落通知，验证 Broker 故障恢复和重复消费。
3. **共享实时接入与异步订阅协调**：实现按股串行的有界处理、纳秒身份／水位、缺口基线，以及多用户去重订阅、预算锁、连接代次与意图版本隔离；取消个人监控与本人规则软删除原子提交，最后需求获实际退订确认后释放名额。
4. **可复现模拟与业务隔离**：复用纯规则状态机，冻结规则／历史／日历／seed，在独立表与 Redis namespace 推进交易时钟；实现离散开盘跳空、批次幂等及进程恢复。V2.1 回归 134 单元、115 不同集成、65 前端／离线探针通过，包含真实／模拟交叉隔离。

不建议将“金融级”“海量高并发”“零丢失”“全局 exactly-once”“实盘每秒数千笔”写进简历；现有证据不能支持这些结论。当前是个人本机工程项目，没有真实多租户生产规模或交易牌照／下单能力。

## 已验证的性能数据与口径

2026-10-31 已增加优化后的 MySQL B+ 树与固定回放对照，见 [新报告](performance/v2.1-rule-selection-2026-10-31/report.md)。原 P5 数值继续作为历史基准保存，不能用“全量读取对照”冒充 MySQL B+ 树优势，亦不可跨两次资源配置比较绝对时间。

来源：[2026-10-29 V2-P5](v2-phase-5.md)。aarch64、Java 25.0.1、10 个可见处理器、最大堆约 4 GiB，Docker 内存约 7.75 GiB，MySQL 8.4.7／Redis 7.4.6／RocketMQ 5.3.2。是单机隔离基准，不是 V2.1 实际 IEX 吞吐或最大容量。

| 场景 | 样本与结果 | 不能推导的结论 |
| --- | --- | --- |
| 万规则，稀疏候选 | 100 个成对样本；ZSet＋Lua P95 1.611 ms／P99 1.951 ms；全量读＋Java 扫描 P95 47.807 ms；差异 0 | 不含锁等待／触发写入，不是完整请求延迟；候选越密，优势越小 |
| 普通模拟 100 交易小时，0 规则 | 6000 点、100 批；60 点批次 P95 53.400 ms／P99 60.597 ms，十页完整读取 | 不能换算成真实行情最高接入速率 |
| 同一点触发 1000 规则 | 25 个样本；批次 P95 1683.614 ms／P99 2059.432 ms；替换清理 P95 799.814 ms／P99 953.120 ms | 大事务有成本；25 样本 P99 即最大值，精度有限 |
| 250 条通知积压恢复 | 人工暂停消费者再恢复，1.078 s 清空、缺失 0；重投十条，额外通知 0 | 是积压消化耗时，不是逐条通知 SLA |
| 通知端到端 | 同一受控故障场景 P95 2763.059 ms | 包含人为暂停，不能宣传“通知始终一秒内” |

V2.1 阶段 4 另做 250／1000 同点规则各 25 次、长实验、独立 Broker 故障和恢复回归，确认行为保留；未把旧微基准重新命名为本次 V2.1 性能压测。未验证集群性能、长期极限容量、断电持久性或全市场数据完整性。

## 关键取舍与面试追问

| 取舍 | 为什么这样做 | 可以继续追问 |
| --- | --- | --- |
| MySQL 真相，Redis 派生 | 缓存只缩小候选，最终状态在事务内决定；token 不一致可重建 | Redis 已更新、MySQL 回滚会怎样？为什么 token 比仅 TTL 更可靠？Redis 宕机为何失败而不是静默跳过？ |
| 按股串行＋股票行锁 | 排序规则编辑与成交判断，减小一致性推理范围；适合当前规模 | 热门单股锁竞争怎么办？跨实例如何保持顺序？队列满为何改变连续性？ |
| Outbox＋幂等，非分布式事务 | 同事务持久意图；允许 MQ 重投，业务约束消除重复结果 | 发成功但标 SENT 失败呢？租约过期并发发布呢？毒消息和重试上限如何观察？ |
| 连接 epoch＋意图版本 | 区分重连旧确认与取消／重加的迟到 ACK | 结果未知何时释放名额？崩溃后如何恢复？为何不能把请求已入库显示为监控中？ |
| 取消规则软删除，历史保留 | 本人订阅与规则同事务停用，不改变他人需求或已发生事实 | 预览后新增规则如何防竞态？取消前的 Outbox 还发吗？再添加会复活旧规则吗？ |
| 连续开盘与故障基线分开 | 可信相邻收盘可判跳空，断线期间未知成交不追补 | 启动当天开盘为什么只建基线？如何验证参考收盘与规则生效时间？如何避免重复提醒？ |
| 模拟复用纯判定、隔离副作用 | 保持边界语义一致，同时禁止污染正式价／规则／通知 | 开盘批次重复请求如何返回原结果？seed 外还要冻结什么？重启后的版本如何兼容？ |
| 不引入微服务／Kafka | 当前规模先保持可验证的事务边界与较低运维成本 | 若扩到多实例，先改连接归属、分片顺序还是 MQ？如何迁移而不丢新事实？ |

## 完成与外部待验

**软件已完成并验证：** 搜索／个人监控／取消原子性／共享动态协调、正式匹配与通知链路、真实及模拟图表、普通与跳空实验、保存恢复与幂等、权限隔离、V9／V10 升级及备份恢复演练。正式库已受控升级 V10，原十五股收到实际订阅确认，正式写入开启。纽约 10 月 30 日 09:30–09:37 实际观察新增 16856 笔已接受 REAL、十五笔启动基线零触发，两次自然普通提醒经正式 Outbox／MQ 唯一落通知；这不是最大吞吐或全天 SLA 证明。

**外部验收边界：** IEX 主动关闭 1006 未消除；当前实际额度只按已配置 15 使用，第十六股及更高额度不宣称通过；正式自然开盘跳空要求连续跨日且真实条件满足，本次重启首笔已验证正确建基线，不能人工制造正式跳空触发。正式运行中本次可执行的只读结果、一次派生索引缺失后自动重建、未发生场景及客户端启动偏差均记录在 [最终交付](v2.1-final-delivery.md)。

封版后转入简历与项目面试准备，不再扩展功能；后续只处理明确故障，不为补齐简历指标改动正式规则或制造成交。
