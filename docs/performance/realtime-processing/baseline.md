## 环境与数据

OpenJDK 25.0.1（Java 21 编译目标），宿主 macOS aarch64／16 GiB／10 核；JVM 可见 2 CPU、768 MiB。独立 MySQL 8.4.7：1 CPU、768 MiB、128 MiB Buffer Pool、`innodb_flush_log_at_trx_commit=1`、`sync_binlog=1`；Redis 7.4.6：0.5 CPU、256 MiB。Hikari 上限 10；每股一个工作线程、队列 1024。正式服务同时保持运行，非独占硬件。

- 每档预热 2s、测量 8s，重复 2 次；单股六场景×五速率，以及 5／15 股两场景×三速率，共 84 档。8s 扫速率不能当作持续容量结论。

- 实际源码摘要与提交 `7171525` 逐文件相符。原记录启动时 checkout SHA 为 `85d308a`（在观测补丁提交前启跑），原始记录保留，不把 checkout SHA 冒充实际测量源码。

## 集中命中与瓶颈

100/s 输入，每轮只有一次集中事件；每格是一次真实命中，样本量不足以给出稳定的条件 P95。这里直接列两个样本，而非用整轮 P95 掩盖它。

| 同笔触发数量 | 两次命中处理时间 ms | 规则 UPDATE | 触发 INSERT | Outbox INSERT |
| --- | --- | ---: | ---: | ---: |
| 100 | 185.1／153.4 | 100 | 100 | 100 |
| 500 | 708.3／686.2 | 500 | 500 | 500 |
| 1000 | 2283.3／1485.4 | 1000 | 1000 | 1000 |

50/s 下 1000 条命中还出现过 4099.2ms／1445.4ms；不能隐藏共享主机波动。该 4099.2ms 样本中，规则状态 UPDATE 为 1211.5ms，触发／Outbox 调用合计 2844.0ms。1000 次状态更新及 2000 次记录写入是实际 JDBC 执行，不是按代码推算。

普通零命中仍执行去重 SELECT、事件 INSERT、流状态 SELECT／写入、股票行锁 SELECT／最新价 UPDATE、事件完成 UPDATE，以及真正的事务提交。Redis 空候选只省规则读取，不能省去这些一致性步骤。

多股共享资源同样受限：第二次 5 股各 200/s 虽未溢出，输入 8s 后仍需 6.10s（零命中）／7.19s（少量命中）排空；15 股各 100/s 需 14.56s／19.53s。队列未满不等于实时。

## 计时与计数限制

- 阶段 P50／P95／P99／Max、采样数、JVM CPU／GC、池活跃及等待、SQL 与 Redis 统计见汇总。阶段可嵌套，不相加伪造整体耗时。
- 事务总计时在 Spring 事务代理外，覆盖 JDBC commit 返回；另列事务体、commit 和队列等待。锁指标是锁 SQL 调用耗时上界，非纯 InnoDB 行锁等待。
- [`LOCK_TIME` 官方定义](https://dev.mysql.com/doc/refman/8.4/en/performance-schema-events-statements-current-table.html)为表锁等待；不能拿摘要 `SUM_LOCK_TIME` 代替股票行锁等待。强制锁竞争用例另验证实际阻塞，InnoDB 状态同时采集。
- JDBC 实际 execute 计数为主。24 档存在数据库摘要差额，逐项保留；独立 15 线程控制用例中 3000 次 SELECT／3000 个成功结果，摘要为 2975。未将差额解释为业务丢行，也未在未经定位时归因于某个 MySQL 内部缺陷。
- 极短纯决策可能低于 `nanoTime` 分辨率，记录到 0ns；采样数来自真实调用，不把未执行阶段填零样本。

## 当前结论

已确认两个不同成本：普通行情的持久化／提交开销，以及集中命中的线性写入尖峰。先选择只减少集中 Outbox 往返的兼容批量方案；保持每条规则乐观更新、逐笔行情事务、股票锁、去重及水位机制。收益必须后续同数据复测，尚不能宣称优化成功。
