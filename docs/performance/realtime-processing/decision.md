# 瓶颈与最小优化决策

决策依据先于实现：[84 档优化前基线](baseline.md)。普通行情仍付出固定持久化和提交成本；集中触发 1000 条规则需要 1000 次乐观更新、1000 次触发插入和 1000 次 Outbox 插入，实测产生秒级单笔尖峰。

## 选择：只对同笔行情的 Outbox 写入做有界批量

保留每条规则的方向／边界判断、乐观版本及状态更新、触发唯一键和快照；每个原有 500 候选分页内收集待写 Outbox，再用受 REAL 来源约束的 INSERT SELECT 一次写入。单条触发继续调用原来的单行 SQL。批量行数必须与输入数量完全相符，否则抛异常，由外层原行情事务整体回滚。

- 不合并行情，不增加单股线程，不改变 1024 队列，不减少股票锁、去重、水位或正式报价持久化。
- 事务边界不变：无论单行或批量，触发与 Outbox 都只在原行情事务提交后可见；第二批失败必须连同第一批、全部规则状态及行情回滚。
- 每个触发仍对应一条 Outbox；aggregate type／event type／schemaVersion／payload 字段、默认状态、唯一约束、发布租约及消费幂等均保持。
- SQL 保留 `quote_events.origin_type='REAL'` 校验，混入不存在或 LEGACY 的触发不能部分提交。通过显式顺序列保持同一分页的插入顺序。
- 额外内存最多一页 500 个小对象；不积累跨行情的缓冲，不引入定时刷新或新的中间件。

这是待复测的实现选择，不预设它能提高普通零命中吞吐。新增单元、隔离事务／来源防线及实际 Broker 回归通过，且同数据复测有收益后才决定保留；本轮不加载正式环境。

## 不采用

- Redis 空候选即跳过事务：会绕开去重、水位和规则生效顺序保护。
- 合并多笔行情事务或直接增加单股线程：会扩大故障回滚范围和改变规则并发线性化边界，本轮没有充分论证。
- 批量规则状态 UPDATE 或触发 INSERT：不是本次最小范围；保留逐条乐观校验及既有生成 ID／快照路径。
- 扩容队列掩盖吞吐不足：只会延长等待。输入持续高于处理能力时，1024 也无法保证实时。
- 立即硬编码个人／全局规则配额：同时命中数量、规则冷却分布、共享资源及产品允许延迟共同决定边界；不能仅据单个合成用户得出个人配额。

## 待复测与运维建议

用相同初始规则／固定输入摘要，复测短矩阵和 60s 重复窗口。低速无丢弃场景另外逐笔核对真实候选 ID 集合、状态变化、最终规则摘要和 Outbox 数量。过载导致实际接纳序列不同的场景不能强求触发总数相等，必须报告舍弃和恢复基线。

积压阈值在最终数据后确定为建议值，尚不变更正式通知。连接故障、订阅异常和队列故障分别观测；长期无成交或休市不代表连接故障。[自然市场与独立产品项](market-acceptance.md)
