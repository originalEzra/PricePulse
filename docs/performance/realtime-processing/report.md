# REAL 行情处理：基线、积压与最小优化

2026-10-31，Australia/Sydney。测量入口是实际单股有界队列，终点是正式业务事务代理返回；不是 Alpaca 网络到通知中心的端到端 SLA。本轮只使用独立合成数据和容器，未加载正式后端。

## 结论先读

1. 单股 100 笔/s 在前后各两次 60s 的零命中／少量命中测试中均无丢弃。150 笔/s 无溢出，但少量命中出现约 0.85–0.91s 的 P95 排队；200 笔/s 多次积压甚至溢出。因此不能宣称稳定承载 200，更不能用短测宣称单股持续 1000 笔/s。
2. 普通行情主要仍付出持久化和提交成本。Redis 空候选没有绕开事务，也没有省掉股票行锁、成交身份、水位及最新价。多股共同竞争限额 MySQL／连接池时，单股顺序队列仍会等待。
3. 保留一项局部优化：同笔行情同候选页的 Outbox 有界批量插入。1000 条集中触发时实际 Outbox SQL 执行从 1000 次降至 2 次，仍写入 1000 行；规则更新和触发插入均未合并。集中命中样本耗时下降，普通路径没有整体提速证据。
4. 新版完整短矩阵反而完成更少、丢弃更多；长窗口也未改善 200/s。负面结果保留，不归因于未经证实的主机原因，不把局部 SQL 收益宣传为整体 TPS 提升。

## 环境、固定数据与复现

详见 [优化前基线](baseline.md)、[参数](plans.json)、[运行命令与统计口径](README.md)。OpenJDK 25.0.1／Java 21 编译目标；macOS arm64，16 GiB，宿主 10 核。实验 JVM 堆 768 MiB、可见 2 CPU、nice 10，**没有硬性限制为两核 CPU 配额**。MySQL 8.4.7 限 1 CPU／768 MiB／128 MiB Buffer Pool；Redis 7.4.6 限 0.5 CPU／256 MiB；Hikari 10；队列 1024，单股一个平台线程。MySQL 持久提交配置未关闭。

- 短矩阵：每档热身 2s、测量 8s、重复两次。单股六场景 × 50／100／200／500／1000 笔/s；5／15 股零命中和少量命中各 50／100／200 笔/s，共 84 档。不是 84 次持续容量证明。
- 每股 1000 条规则（零规则除外）；ACTIVE／COOLDOWN、ABOVE／BELOW；少量命中为两条近价 REPEAT 配合固定路径，100/s 示例有 80／800 笔非空候选。集中命中为指定 100／500／1000 条 ACTIVE ONCE，在每轮一次跳价中同时触发；不会逐笔偷偷重置规则状态。
- seed `2026103101`；固定事件时间与价格，接收／入队／工作开始／提交返回另计。生产过期与连续性判断仍执行。
- 长窗口：单股零命中／少量命中，100／150／200 笔/s，每档 60s、两次重复，`boundary` 模式。它与精细 SQL 计时的 `full` 模式分别比较。
- 原始逐笔 CSV.gz 与每秒资源快照留在忽略的 `target/pipeline-{before,after}-{final,sustain}-20261031/`，仓库只保留安全合成汇总与原文件 SHA-256／字节数。原基线启动 checkout SHA 早于观测补丁提交，实际源码摘要对应 `7171525`，未改写旧记录。

两次短矩阵 84／84 固定输入摘要相同，83／84 初始规则摘要相同。`FEW_HIT-1000-2` 的热身处于过载，初始状态不相同；不把它当成严格同状态的因果对照。旧版 `ZERO_HIT-15stocks-100-1` 热身保留 `CannotCreateTransactionException`，但测量期成功；原记录没有保存热身异常次数及底层原因，该档标记不适合干净汇总。完整档位保留，不删除异常行。

普通零候选此档每笔有 7 次业务 Mapper SQL：股票锁、身份查询、事件插入、流状态读取与 upsert、最新价更新、事件完成；另有 JDBC 事务控制及提交等开销。Redis 只能减少规则表候选读取，不能推断不再访问 MySQL。

## 旧／新／旧控制与逐笔一致性

大矩阵结束后，使用同一版注入／观测工具，按旧 evaluator→当前 evaluator→旧 evaluator 的顺序各跑 24 档：单股、100／200 笔/s、六场景、热身 2s／测量 4s／重复两次。三轮各 14400 笔、均无失败或丢弃；这仍是短窗口控制，不能用于持续容量承诺。

两组比较均核验：固定输入、初始和最终规则摘要、每笔实际候选 ID 摘要、处理结果、触发／重新激活次数、触发及 Outbox 行数。各 24 档／14400 笔全部一致。[首次对照证明](functional-comparison.json)、[末次旧版对照证明](functional-comparison-late.json)。这些是实际结果对比，不只是分别运行纯状态机 oracle。

| 约束／异常 | 证据 |
| --- | --- |
| 创建、修改、暂停、恢复、删除与行情并发 | 正式 RuleService 的 50 次生命周期事务与 120 笔行情并发；规则及触发结果保持约束 |

| 运行时指标 | 默认关闭；显式开启后实际 runtime lane 的处理／提交计时和退订清理通过；观测异常不改变业务返回或异常 |

[独立真实数据库正确性记录](correctness/summary.json)含 8 项通过检查及 1 项 SQL 计数诊断。满队列受控恢复中，故障到新基线提交 38.11ms、到队列排空 38.48ms；这是单次受控阻塞夹具，不是自然持续过载的恢复 SLA。长窗口的排空耗时也不能冒充持续输入下的恢复速度。

SQL 诊断实际执行 3000 次 SELECT、获得 3000 个结果，数据库摘要为 2967；该项 **没有标 PASS**。保留 33 次差额，不能用它证明业务丢失或给出未经定位的数据库原因。单股严格控制轮中的 JDBC／摘要执行次数相符，批量 SQL 减少结论同时有实际行数验证。

30 秒异常告警方面，只能确认现有故障分类和单连接尝试内的去重。`MarketFeedHealth` 保留最近 20 次失败及最后失败时间，重试会更新最后时间；当前没有跨重试 incident 起点／恢复闭合模型。持续时间与跨重试去重不满足独立正式告警所需证据，不能标为完成。

## 积压治理决策与尚未实施项
