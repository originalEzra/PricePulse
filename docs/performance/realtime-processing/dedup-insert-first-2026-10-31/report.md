# INSERT 优先成交去重：正确性及性能对照

实验从 2026-10-31 晚持续至 11-01 凌晨（Australia/Sydney）；逐轮起止时间统一记录 UTC。

## 结论：不保留为默认实现

候选 B 通过正确性验证，也确实减少正常路径的一次 SELECT，但没有同时满足跨负载的可信收益及异常／积压路径可接受这两个条件。**最终工作树已恢复 A，全部生产源码与开始时 `30df066` 逐字节相同。** B 保留在本地候选提交 `2e3112a`，可通过隔离工具复现；没有上线。

- 零规则、零候选有改善；例如零候选 100/s 的五组平均处理耗时都下降，处理 P95 中位数 7.655→6.113ms。
- 少量命中 150/s 只有 2／5 组平均处理耗时改善；处理 P95 中位数 8.546→13.515ms，排队 P95 中位数 6.916→875.443ms，含排空的完成速率 149.6→138.9/s。
- 已有重复的直接事务路径 P95 2.509→3.455ms；并发同键路径 P95 6.803→10.168ms。后者每对 SQL 总次数仍为 9，未获得查询次数收益。
- 5% 重复混合负载的部分中位数改善，但不是每组都改善；B4 最后一个 200/s 档额外排空 4.42s。它与所有有利结果一起保留。

共享宿主和运行期波动可能影响这些差额，当前证据不能将所有退化确定归因于 B；同样不能据此豁免负面结果、只挑零命中宣称优化成功。本轮不继续寻找更有利的环境／样本，也不实施其他方案。

本轮只研究删除正常成交的前置 `findByEventKey`。以实际工作区 `30df066` 为 A，候选 `2e3112a` 为 B；新建本地分支 `codex/pricepulse-insert-first-dedup-20261031`。开始时工作区干净。A 已包含上一轮未正式加载的有界 Outbox 批量，两边完全相同，不将两轮收益混算，也不把当前源代码当成正在运行的正式版本。

## 最小实现与边界

候选的生产改动只有 QuoteIngestionService，现[工作树中的文件](../../../../src/main/java/com/ezra/pricepulse/market/QuoteIngestionService.java)已恢复 A。B 保留股票 FOR UPDATE 后的价格规范化，直接构造 RECEIVED 事件并 INSERT；成功后原流程继续。仅当异常链中的 JDBC 错误同时为 1062／23000 且服务端错误尾部明确指向 `quote_events.uk_quote_events_event_key`，才回查已有事件并调用原 `duplicate()`。内容一致返回 DUPLICATE，不一致继续抛 CONFLICT，找不到行仍抛原异常。

没有改 Mapper／XML／唯一索引、READ_COMMITTED、股票锁、规则生效顺序、纳秒水位、RECEIVED／PROCESSED／DISCARDED、Redis、Outbox、RocketMQ 或真实／模拟隔离。没有内部重试、INSERT IGNORE、UPSERT、行情微批或队列调整。

错误匹配使用末尾完整表名／约束名，不搜索用户可控的重复值。缺少 JDBC 信息、未知语言／驱动格式、其他表同名约束、PRIMARY／其他索引、死锁和连接错误均不转成 DUPLICATE。实测环境为 MySQL 8.4.7／en_US；这不是跨数据库、跨语言格式的通用异常解析器。正式加载前仍需确认运行环境符合该条件。

失败 INSERT 可能消耗 AUTO_INCREMENT 值。新事件 ID 出现更多间隔不表示丢成交；原有事件 ID 不改。功能对照采用事件真实键、纳秒时间、价格、候选规则和状态，不错误要求 A/B 新生成的代理 ID 连号相同。

## 先行正确性验证

[完整检查记录](correctness.json)、[测试数量及源代码一致性](validation.json)。最终完整表名候选先完成 154 个不同单元、75 个相关集成以及 17 项真实事务正确性检查，均通过；最终复验的 55 个相关单元包含在 154 中，不重复相加。

| 场景 | 结果／证据 |
| --- | --- |
| 首笔成交及规则触发 | 正常 INSERT→处理；状态、触发、Outbox 正确 |
| 同键同内容 | DUPLICATE；报价、股票最新值、流状态、规则、触发、Outbox 的行数据指纹不变 |
| 同键不同内容 | 价格、1ns 时间差、来源、sequence、provider、feed 和 LEGACY 来源分别拒绝；跨股票全局键竞争一条成功、一条 CONFLICT |
| 其他唯一键 | 在隔离表添加不同唯一索引，真实 1062 原样传播、事务回滚；不误判为事件重复 |
| 其他 SQL 错误与重试 | MySQL trigger 注入失败后无残留副作用；撤销故障，同一身份可成功重试且仅触发一次 |
| 并发相同成交 | 两个服务线程保留同股锁；一个 PROCESSED、一个 DUPLICATE，只增加一条成交、触发和 Outbox |
| 捕获后的事务可用性 | 外层 READ_COMMITTED 中先处理真实重复，再 SELECT 和写入下一笔；rollbackOnly=false，实际提交成功，没有 UnexpectedRollbackException |
| 唯一键等待 | 底层 Mapper 受控等待约 157／161ms；持有者提交时得到真实 1062 并能在当前事务读取，回滚时另一 INSERT 成功 |
| 共享记录锁与死锁 | 无股票锁的独立 JDBC 诊断复现一个成功、一个 1213；失败方显式回滚。它不替代生产入口，服务不吞 1213 或假称 DUPLICATE |
| 行情失败、过载、规则并发 | 原 1024 溢出／首笔基线、真实 MySQL 工作异常、50 次规则生命周期与 120 笔行情并发等检查保持 |
| 批量与真实来源防线 | 千条触发第二页失败整事务回滚；REAL／LEGACY 混合拒绝；重试与消费幂等保持 |
| 正式通知机制回归 | 独立 Broker／Topic 实际发布、重复投递、消费；不会向真实用户或正式 Topic 发送测试消息 |

重复键回滚语句与死锁回滚整个事务需要区分。Spring／MyBatis 是否标 rollback-only 还取决于异常传播边界；这里验证的是项目实际 SqlSessionTemplate／事务代理，而不是仅凭官方描述推断安全。[官方依据与复现命令](README.md#正确性优先)

候选正确性原始记录的 checkout SHA 早于候选提交，代码当时尚未提交；其实际源文件 SHA 与 `2e3112a` 一致，且当时所有已跟踪生产文件与两份通过的候选构建逐字节一致。最终恢复 A 后的验证另记，不能把候选构建当成最终工作树。没有用 checkout SHA 冒充干净工作区的证据。

原有 Performance Schema 并发计数诊断单独保留：实际 3000 次 SELECT／3000 个结果、摘要 2991，差额 9 未标为 PASS，也不因该轮 SQL 优化宣称修复。业务 SQL 次数以实际 JDBC execute 埋点为准，数据库摘要差额不强行校正。

## 实验与统计口径

五组 A→B 交替，共十个独立 JVM／MySQL／Redis 运行，每轮 16 档；参数、唯一索引、源码摘要、UTC 时间、原始文件摘要全部保留。源文件变化、任务失败或热身异常会停止，不自动补跑替换。计分前的旧版工具试跑保留并明确排除，详见 [实验入口](README.md)。

- 单股、队列 1024、单线程；规则 0 或 1000 条；50／100／150／200 笔/s；每档预热 2s、测量 8s。固定 seed、原有混合价格路径。
- 四场景：零规则、千规则无候选、两条近价重复规则、相同少量命中配置＋5% 重复输入。重复的 eventKey／价格／事件时间／来源一致，接收和测量任务独立，不能用事件键覆盖原始样本。
- 每轮另测已有重复 200 次、内容冲突 200 次、100 对并发同键请求；明确为直接事务代理调用，无队列，也不称为持续行情输入能力。
- MySQL 1 CPU／768 MiB、Buffer Pool 128 MiB、持久提交开启；Redis 0.5 CPU／256 MiB；Hikari 10；JVM 768 MiB、2 个可见 CPU（非两核硬配额）、nice 10。与正式应用共享宿主，不能冒充独占硬件。
- 事务总计时覆盖真正提交，CONFLICT 路径则覆盖回滚完成。股票锁指标为整个锁 SQL 调用，含网络／执行，不能当纯锁等待。阶段嵌套，不相加伪造整体。
- 每次 SQL execute 实际记数，包括失败 INSERT；不含 JDBC 事务控制、采样查询或连接管理。查询减少只针对业务 SQL，不等于 MySQL 总访问量或总成本下降相同比例。
- 每轮独立求 nearest-rank P50／P95／P99，再报告五次统计量的中位数、范围及每次值；不将大量逐笔样本当成独立实验次数。全部负面结果保留。
- PROCESSED 吞吐和全部已处理请求吞吐分开：重复不是新增有效成交，也不是积压。过载舍弃与成功样本延迟同时展示。

8s 窗口可比较完整处理耗时与短期积压，不能推出长期持续容量。没有将本轮总时长或多个短窗口相加，冒充某档连续运行时间。

## 保留条件逐项结论

| 条件 | 本轮结论 |
| --- | --- |
| 正常路径实际少一次查询 | 满足 |
| 关键幂等、并发、事务回归 | 候选在已验证边界满足 |
| 成交、规则、触发、Outbox 一致 | 满足，80 个严格配对全量核对 |
| 可比较重复实验有可信整体改善 | 部分场景改善，未能跨关键负载成立 |
| 积压与重复异常路径无不可接受退化 | 未满足保留门槛；上述尾延迟及排队退化不能忽略 |

**最终选择保留 A。** 不能把本次成果写成已落地的吞吐提升；可以准确描述为完成单变量对照、验证 SQL 节省但依据尾延迟／异常成本否决默认采用。
