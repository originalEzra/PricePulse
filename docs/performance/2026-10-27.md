## 候选选择

每档 10 对预热、150 对计时，查询顺序交替；逐次比较候选 ID 集合。

| 单股规则数 | 全量读取 + Java 筛选 P95 | ZSet 区间查询 P95 | ZSet P99 | 平均候选数 | 结果不一致次数 |
| --- | --- | --- | --- | --- | --- |
| 1,000 | 11.403 ms | 1.874 ms | 3.682 ms | 0.48 | 0 |
| 10,000 | 46.680 ms | 1.398 ms | 1.719 ms | 4.73 | 0 |
| 50,000 | 259.928 ms | 2.066 ms | 2.964 ms | 25.61 | 0 |

这些数字只衡量稀疏价格穿越时的候选选择，不包含股票锁等待、提交或触发持久化。基线确实读取全部可索引规则，不是经过 SQL 范围索引优化的 MySQL 实现。

5 万条规则的三次冷重建分别为 359.424、359.215、408.086 ms。热查询变快不代表冷恢复没有成本；单股大索引重建仍占用股票锁并执行 Redis Lua。

## HTTP 行情请求

带真实 JWT 的本机 /api/market/replay 请求，每请求一条行情，每股 1000 条规则，不触发提醒。

| 请求线程 / 股票数 | 有效计时请求 | 观测吞吐 | P95 | P99 | 错误 |
| --- | --- | --- | --- | --- | --- |
| 1 / 1 | 100 | 94.85 请求/s | 12.858 ms | 22.406 ms | 0 |
| 4 / 4 | 400 | 268.31 请求/s | 21.095 ms | 31.851 ms | 0 |

这是每股串行、股票间并行的短时闭环负载；没有寻找系统饱和点，不能把 268 请求/s 写成“系统最大 QPS”或并发用户容量。最后核对了全部计时、预热和基线行情的持久化数量。

触发记录到通知创建的 P95 / P99 为 3864.436 / 3876.385 ms，包含有意暂停消费和发布时间，不表示常态实时通知延迟。清空时间按 50 ms 轮询观测，包含消费者恢复调度。

这个实验还说明：500 条规则一起触发时，触发事务本身接近一秒。MQ 解耦了通知处理，但不会消除状态修改、快照和 Outbox 写入成本。

## 故障对账

| 实验 | 实际操作 | 对账结果 |
| --- | --- | --- |
| 发送失败 | 注入两次发送异常，再恢复真实发布器 | 2 个 FAILED 任务最终生成 2 条通知，约 188.491 ms |
| 发布确认窗口 | 实际取得 SEND_OK 后不写 SENT，等待租约回收 | 实际投递 2 次、生成通知 1 条，约 1100.751 ms |
| Redis 恢复 | 真实停止/重启临时 Redis，失败行情使用原事件键重试 | 故障行情回滚；重试触发 1 次，再次重试为 DUPLICATE；约 2058.962 ms |

前两项模拟的是发送异常和崩溃窗口，没有关闭共享 Broker，也没有强杀应用进程。测试租约为 1 秒、初始退避为 100 ms；日常默认是 30 秒和 2 秒。发布器由测试主动调用，不包含正常扫描周期的额外等待。

~~~

初次完整试跑在 Redis 恢复检查失败，状态保存为 FAILED；固定临时 Redis 重启前后的映射端口后，先以小规模验证，再重新运行完整规模并得到本报告。这里没有把失败那轮的部分结果拼成通过报告。

本次验证可支持“稀疏候选查询明显减少全量读取成本”和“测试故障窗口下业务对账正确”的结论。尚未覆盖长期稳定性、热点单股饱和点、跨机网络、集群故障、Broker 断电和真实进程强杀。AI 调用不在本次实验范围内。
